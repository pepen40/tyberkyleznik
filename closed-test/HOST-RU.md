# Запуск отдельного закрытого теста

> Архивный необязательный вариант. Владелец сменил цель на обычные GitHub Pages
> и существующий Supabase. Для этой цели не нужен Linux-хост или этот сценарий.
> Используйте [актуальный план](../docs/public-playtest.md).

Сервер пока не предоставлен и не запущен. Владелец выбирает уже доступный ему
отдельный Linux x86_64 хост (ориентир: Ubuntu 22.04, как проверенный CI runner),
передаёт друзьям только SSH-доступ для туннеля и отдельные игровые пароли.
Облачные ресурсы автоматически не создаются. Production Supabase не нужен.
Рекомендуемый запас для Docker-стека: 4 CPU, 8 ГБ RAM, 30 ГБ свободного диска;
это запас для тестирования, не измеренный минимальный размер сервера.

## 1. Подготовка владельцем

Нужны исходящий HTTPS к GitHub, nodejs.org, npm, Docker registry и CDN библиотек
в браузерах. Входящий доступ разрешается только к SSH, по возможности с IP друзей.
Порты 8080, 54321, 54322 и остальные Docker-порты наружу не открывайте.
Не используйте общий production-хост. Docker-доступ даёт административные
возможности: он нужен только оператору, никогда SSH-пользователям друзей.

На выбранном Ubuntu-хосте установите системные зависимости:

```sh
sudo apt-get update
sudo apt-get install --yes git curl ca-certificates xz-utils postgresql-client openssh-server
```

Docker Engine устанавливается оператором по официальной инструкции для Ubuntu:
https://docs.docker.com/engine/install/ubuntu/ . Нужен работающий локальный daemon
и доступ оператора к его Unix socket. Скрипты не меняют Docker/SSH/firewall системы.
Отдельный Compose-файл отсутствует: закреплённый Supabase CLI сам управляет
контейнерами. Наличие Compose plugin проверяется информационно.

Под обычным пользователем оператора, без `sudo` для Node/скриптов:

```sh
umask 077
git clone --single-branch --branch audit/site-completion-20261103 https://github.com/pepen40/tyberkyleznik.git tyberkyleznik-test
chmod 700 tyberkyleznik-test
cd tyberkyleznik-test
git status --short --branch
git rev-parse HEAD
bash closed-test/install-host-tools.sh
bash closed-test/host.sh doctor
```

Установка инструментов ограничена игнорируемым `.runtime/host-tools`: Node22.23.4
проверяется по официальному SHA256 manifest, CLI закреплён на 2.84.2 через npm.
Глобальные Node/CLI не меняются. Уже установленные Node22/CLI2.84.2 можно использовать
без install-host-tools.sh. Хостовые пакеты и установка инструментов здесь не запускались.

Ожидается `PASS` для Linux, Node, Docker daemon, CLI, psql, Git, SSH. При ошибке
исправьте указанную зависимость. `doctor` запрещает удалённый Docker context и
унаследованные SUPABASE_* credentials/URL; значения секретов он не печатает.
Не экспортируйте production `.env`, не выполняйте `supabase login/link`.

## 2. Создание тестового backend — один раз

```sh
bash closed-test/host.sh init
```

Команда последовательно выполняет уже проверенные prepare/start/apply. Создаются
новый project ID, случайные JWT-ключи и новая TEST-схема с компонентными миграциями.
Docker-публикации проверяются на 127.0.0.1/::1. Это не восстановление production.
Если init прервался, не запускайте его повторно поверх каталога и не делайте reset:
сохраните данные, выполните stop, выясните причину. Новая сессия возможна в новом
каталоге, например `bash closed-test/host.sh init .runtime/friends-session-02`;
этот же путь затем передаётся edge/web/verify/stop и add-user.

В двух отдельных приватных терминалах оператора из каталога checkout запустите:

```sh
bash closed-test/host.sh edge
```

```sh
bash closed-test/host.sh web
```

Оставьте их открытыми на время теста. Автостарта при перезагрузке нет. В третьем:

```sh
bash closed-test/host.sh verify
```

Ожидается `PASS`: сгенерированные локальные ключи, frontend/proxy, Auth и оба Edge
endpoint, отвергающие анонимный доступ. Проверяются запрет admin/signup, закрытые
файлы и отсутствие hosted Supabase URL в отдаваемом script.js. Проверка не печатает
ключи и не имитирует успешный игровой вход. Если Edge ещё загружается, дождитесь
готовности терминала edge и повторите verify. При ошибке наружный доступ не выдавайте.

Исходный script.js сохраняет существующий production public URL/key для обычного
сайта; закрытый сервер заменяет их только в HTTP-ответе на same-origin `/backend`
и новый локальный anon key. Service-role остаётся у backend и не отдаётся браузеру.

## 3. Выдача игровых аккаунтов

В приватном интерактивном терминале, без записи сессии/`tee`/перенаправления:

```sh
bash closed-test/host.sh add-user .runtime/closed-test-stack friend_one
bash closed-test/host.sh add-user .runtime/closed-test-stack friend_two
```

Имя — 3–20 букв/цифр/подчёркиваний. Скрипт создаёт синтетический Auth-аккаунт,
допуск и профиль, затем реально проверяет вход с тем же паролем. Пароль показывается
один раз; передайте каждому его собственную пару приватно. Это обычный тестовый
пароль, он действует до конца сессии, а не одноразовый код. Не используйте реальные
пароли, не вызывайте seed-ci для друзей, не раздавайте `.env` или service-role.
Пароли существующих аккаунтов повторной командой не сбрасываются; при потере
выдайте новое уникальное имя. Открытая регистрация запрещена сервером.

## 4. Доступ и приёмка

Сначала настройте [ограниченный SSH для каждого друга](SSH-RU.md). До приглашения
друзей проверьте туннель с отдельной SSH-учёткой, вход двумя выданными игровыми
аккаунтами, приглашение и один ход. Это приёмка конкретного хоста; успешный CI
не подтверждает его firewall/sshd/доступность CDN. Фактическая приёмка хоста ещё не выполнена.

Поддержаны шахматы/reconnect/чат, PvE и серверный PvP с тестовым предметом.
Валюта, награды, рейтинг, покупки/продажи/кейсы/ежедневные начисления отключены
сервером. PvE-прогресс только в сессии. Произвольные игры/все боты/реальные мобильные
устройства не сертифицированы этим этапом. Сессия ограничена 24 часами от init.

## 5. Остановка и проблемы

Сначала Ctrl-C в терминале web: друзья сразу теряют frontend и WebSocket-соединения.
Затем Ctrl-C в edge и в третьем терминале:

```sh
bash closed-test/host.sh stop
```

Данные не удаляются. Не выполняйте `docker system prune`, `db reset`, `migration
repair`, production deploy или ручное включение наград. После 24 часов заведите
новую отдельную сессию вместо продления/переписывания базы.

- `doctor` не видит Docker: исправьте локальный daemon/права оператора; не переключайте
  его на удалённый production daemon и не запускайте сайт от root ради обхода.
- verify сообщает 502/503: проверьте открытые терминалы edge/web, сеть загрузки
  зависимостей и повторите verify после готовности; не ослабляйте Auth/RLS.
- SSH работает, сайт нет: используйте именно `127.0.0.1:8080`, проверьте web и
  `PermitOpen`; при занятом локальном порте друга используйте 18080, как в SSH-RU.md.
- Для немедленного прекращения всего теста остановите web и stack. Удаление ключа
  SSH блокирует новые подключения, но не обрывает уже открытый туннель; Realtime
  тоже может кешировать разрешения до отключения. Не удаляйте аккаунты/данные.

При неясной ошибке оставьте доступ закрытым и сохраните текст ошибки без `.env`,
паролей, JWT, Auth responses и сырых Docker inspect. Следующий запуск согласуется
с оператором. Отсутствующие 25 исторических SQL не блокируют этот отдельный профиль.
