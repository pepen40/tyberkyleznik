# Обычная игра с друзьями через GitHub Pages

Цель с этого этапа: существующие GitHub Pages и Supabase. VPS, отдельный Linux-хост,
SSH-туннель, выданные через host.sh аккаунты и платная инфраструктура не нужны.
`closed-test/` остаётся необязательным CI-стендом; не запускайте его инструкции
для доступа к обычному сайту и не применяйте его TEST SQL к существующей БД.

## Что подтверждено сейчас — 2026-11-04

Read-only GET https://pepen40.github.io/tyberkyleznik/ вернул HTTP200; в HTML есть
экраны входа и игры. GitHub metadata подтверждает `has_pages=true`, default branch
`main`, текущий main SHA `27fcc2ece27db3cba2c435c5c024c1bd7ab62f3b`.
Настройка источника публикации Pages через Settings не проверена; нельзя считать,
что push audit-ветки публикует сайт или что Pages точно соответствует этому main SHA.

Публичный script.js использует hosted-проект `zfvinbamwavibnhmfwnz`,
Supabase Auth signInWithPassword/signUp и
приватные каналы. Он ещё читает players напрямую и отправляет клиентский
`pvp_result` с `{win:isWin}`. В нём отсутствуют `get_player_profile`, адаптер
`createServerChessInvitations` и вызов нового `rpg-pvp`. Это подтверждённое отличие
от проверенной audit-ветки, а не доказательство того, что текущий сервер принимает
поддельные награды. Производственный Edge source сейчас не прочитан.

Попытка read-only `list_migrations` через существующий Supabase connector завершилась
`OAuth token refresh failed: Failed to parse server response`. Production SQL,
вход в аккаунты, выдача наград и запросы изменения данных не выполнялись. Актуальные
RLS/RPC/Auth/Realtime/Edge версии поэтому не подтверждены. Ранний снимок отсутствия
новых PvP миграций и `rpg-pvp` — историческое свидетельство, не свежая инвентаризация.

## Архитектура и минимальная совместимость

Браузер получает index.html/CSS/JS/изображения с Pages. Он напрямую обращается к
существующему Supabase: Auth для сессии; проверенные Edge Functions для профиля,
приглашений, чата и PvP; приватный Realtime для доставки; PostgreSQL RPC/RLS для
допуска и авторитетных игровых действий. GitHub Pages не должен исполнять серверный
код. Service-role ключ остаётся только в Supabase; public/publishable key в браузере
не заменяет серверную авторизацию.

В обычном клиенте `PEPEN_CLOSED_TEST` не устанавливается, в обычном backend не
включается `PEPEN_CLOSED_TEST=true`. Допуск по синтетическому allowlist и тестовая
схема не требуются. Обычная регистрация остаётся существующим Auth-процессом;
её триггер создания профиля и разрешённый способ регистрации нужно подтвердить
в реальном проекте. Нельзя подставлять закрытую TEST foundation вместо него.

Новый клиент требует совместимых `get_player_profile`, invitation ledger/RPC,
приватных политик и `rpg-pvp`. Одной публикации HTML/JS недостаточно. Сначала нужна
проверка/согласованное обновление существующего backend, затем публикация клиента.

## Игровые возможности и ограничения

| Функции | Что можно сохранить для обычной игры |
| --- | --- |
| Мини-игры, Simon, PvE RPG, шахматы с ботами, настройки/виджеты | Не отключать ради теста. Можно играть без выплат; охват всех мини-игр/ботов/устройств пока не полный |
| Онлайн-шахматы, приглашения, reconnect, чат | Реальные два клиента прошли изолированный E2E; разрешать на сайте после подтверждения соответствующего deployed backend и двухаккаунтной проверки на Pages |
| RPG/PvP, атаки, идемпотентные повторы, предметы из имеющегося инвентаря, timeout | Серверная игровая логика проверена на disposable БД, включая настоящий browser timeout; существующий backend/владение сессиями нужно сверить перед публикацией |
| Чтение профиля, инвентаря, таблицы прежних результатов, экипировка уже имеющегося | Не равно новой выдаче/начислению; сохранить при подтверждённом RLS и правах соответствующих RPC |
| Награды за победы, новые монеты/рейтинг/онлайн-рекорды | Не включать: шахматы/PvE/Simon/roach результаты ещё клиентские. Даже серверно проверенный PvP не включает выплаты автоматически |
| Покупки/продажи, кейсы, покупка улучшений/экипировки, выдача предметов/claims | Приостановлены в подготовленном server source до проверки deployed транзакций и зависимостей. Это запрет экономических операций, а не запрет самих игр |

`award-coins` теперь содержит общий `isEconomyPausedAction` guard **для обычного
режима**, не зависящий от browser flag/closed-test allowlist. Он возвращает
`rewardPaused:true` до dispatch/RPC для начислений, claims (включая spend500),
кейсов и торговых/покупочных действий. `pvp_result` отсутствует в allowlist и
отклоняется. Экономические экраны не удалены, игровые механики не менялись.
Этот guard пока существует только в ветке; текущий публичный backend им не объявлен защищённым.
Прямые права на старые привилегированные RPC также требуют read-only проверки:
Edge guard не заменяет их ACL/RLS. Настройки production не менялись.

Изменение source сохранено в `7204de7fbe5d69e258ed991daf9e681f00de7b33`.
`node tests/run-public-economy.cjs` сначала воспроизвёл отсутствие общего guard,
затем прошёл: реальные ветви отказа не доходят до экономического dispatch.
Также прошли релевантные `run-server-invitations.cjs` (5 случаев),
`run-account-callbacks.cjs` (10 stale + 10 current случаев), выполнение actual
economy-policy.ts через Node22 с type stripping, YAML parse и git diff --check.
Это локальные source/regression проверки, не production интеграция. Deno-тесты
новой policy подключены к CI; локально Deno не запускался. Предыдущие PostgreSQL,
полный игровой E2E и migration recovery не повторялись. Новый production smoke
не запускался и не объявляется пройденным.

## Что нужно от владельца и порядок запуска

1. Восстановить подключение Supabase connector штатной авторизацией, чтобы можно
   было прочитать текущие migrations/tables/RLS/RPC/Edge metadata/source. Не присылать
   токены/service-role в чат и не извлекать credential helper. До этого состав
   необходимых серверных изменений остаётся условным.
2. Проверить Settings → Pages: фактический источник публикации, ветку/каталог или
   workflow. Предоставить возможность read-only проверки этих настроек либо их
   значения. Сайт уже существует, новый адрес/хостинг создавать не требуется.
3. После сравнения получить **отдельное разрешение на точный production-план**:
   сначала закрытие legacy выплат и опасных прямых RPC, затем только недостающие
   совместимые миграции/политики и matching `award-coins`/`rpg-pvp`. Список десяти
   кандидатных игровых миграций находится в rpg-pvp-production-rollout.md; это не
   команда применять их вслепую. Сначала проверить зависимости, backup и реальное
   состояние. Потерянная история из 25 исходников остаётся ограничением полного
   bootstrap; поиск не повторялся. Ни синтетический baseline, ни repair/reset
   существующей БД не являются путём публикации.
4. После успешной проверки backend отдельно разрешить публикацию согласованного
   клиента через существующий Pages-процесс. Merge/deploy этого этапа не выполнялись.
   Не включать closed-test флаги и не запускать host.sh.
5. На реальном URL пройти два отдельных браузера/аккаунта: вход/восстановление,
   приглашение/блокировку, ходы шахмат, reconnect/пропущенный ход/чат/сдачу; RPG
   приглашение/действие/повтор/timeout/смену аккаунта. Проверить, что запрещённые
   начисления не меняют баланс/рейтинг/инвентарь. Это изменение production игровых
   данных тестовых аккаунтов, поэтому сейчас такой smoke не запускался.
6. Только после приёмки отправить друзьям обычную ссылку на Pages. Они открывают
   сайт в браузере и пользуются подтверждённым штатным Auth-входом/регистрацией.
   Ни SSH, ни CLI, ни Docker на компьютерах друзей не нужны.

Нет необходимости покупать сервер. В рамках текущего запрета на production-изменения
можно подготовить код и план, но нельзя выдать проверенный audit-клиент за уже
развёрнутую версию. Текущий статус: публичная страница доступна, безопасная готовность
всей опубликованной игры не подтверждена; rollout ожидает read-only доступа и
отдельного разрешения на конкретные backend/Pages изменения.
